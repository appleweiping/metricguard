# MetricGuard 0.2.0

Released 2026-08-31.

MetricGuard 0.2 adds dependency-free text-similarity metrics, strictly paired statistical
comparison, direction-aware CI gates, and opt-in metric plugins while retaining the v0.1 case and
reporting workflows.

## Highlights

- New built-ins provide pairwise ROUGE-L, sentence BLEU, and normalized Levenshtein similarity.
  Their documented local semantics are the contract; they do not claim byte-for-byte equivalence
  with third-party metric packages.
- Baseline and candidate reports are aligned by case ID and must have identical references and tag
  sets. Record and tag order may differ. A one-sided undefined-result skip is rejected rather than
  comparing different populations.
- Comparison reports include a deterministic paired percentile-bootstrap interval and a separate
  two-sided paired sign-flip Monte Carlo randomization p-value. JSON and Markdown schemas are
  versioned, with overall and tag-grouped summaries.
- Regression gates record an explicit `higher` or `lower` optimization direction. Raw deltas remain
  `candidate - baseline`; gate values are oriented so positive consistently means improvement.
- The explicit metric registry supports opt-in `metricguard.metrics` entry-point discovery with
  validated factory results, name-conflict checks, fresh option mappings, and atomic registry
  updates. Baseline and candidate evaluation use the same metric configuration.
- CLI output collision checks protect inputs and existing outputs, including hard-link aliases.
  A reproducible benchmark script records its generated workload and environment as JSON.

## Compatibility and migration

The v0.1 strict JSON/JSONL case format, exact/token-F1/character-F1/numeric metrics, undefined-result
policies, single-suite reports, and CLI evaluation flow remain available. Existing workflows do not
load third-party plugins unless explicitly requested.

All built-in metrics are higher-is-better. A lower-is-better plugin or external score must set the
comparison direction explicitly; otherwise a regression could be interpreted as an improvement.

## Verification

The release candidate passed 188 tests with 93.99% branch coverage. Ruff, strict mypy, source/wheel
builds, and an isolated wheel smoke test passed. Tests cover alignment permutations and rejection
cases, direction-oriented gates, deterministic resampling, p-value boundaries, plugin failures and
rollback, and CLI hard-link protection.

## Known boundaries

- `probability_improvement` is descriptive bootstrap mass above zero in the configured direction,
  with ties receiving half weight. It is not a posterior probability that the candidate is better.
- The p-value validity depends on paired exchangeability. The percentile interval and sign-flip
  p-value answer different questions, and the smallest possible reported p-value is
  `1 / (samples + 1)`.
- Resampling cannot detect benchmark bias, contamination, invalid references, or a metric that does
  not represent product quality.
- Plugin discovery imports executable third-party code with the current process permissions. A
  failed registration is rolled back atomically, but import-time side effects cannot be undone;
  paired plugins must also be deterministic.
